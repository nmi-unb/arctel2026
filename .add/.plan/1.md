A partir do contrato descrito em `NOTICE_LINK_INTEGRATION.md`, a próxima etapa não é começar diretamente pela interface. Primeiro é necessário fechar algumas decisões de arquitetura, validação e fluxo de gravação.

O contrato já estabelece que:

* `avisos.json` guarda os avisos, mas não deve armazenar URLs de aulas;
* links de aulas são resolvidos por `moduleId`, `lessonId` e `linkType`;
* `staticLink` serve para links que não pertencem a aulas;
* `url` é apenas legado e deverá ser removido;
* um aviso pode existir sem qualquer botão;
* falhas na resolução de links não devem impedir a exibição do aviso. 

## 1. Definir o escopo exato do editor

A primeira decisão é estabelecer quais arquivos o programa Flet poderá editar.

Há três possibilidades:

### Opção A — editar somente `avisos.json`

O aplicativo cria, edita, arquiva, duplica e remove avisos, mas apenas referencia módulos e aulas já existentes.

É a opção mais segura para a primeira versão.

### Opção B — editar avisos e links das aulas

Além de `avisos.json`, a interface edita:

```text
assets/data/modulos/modulo-1.json
...
assets/data/modulos/modulo-11.json
```

Isso permitiria cadastrar na mesma aplicação o link do Teams, da live ou da gravação.

### Opção C — administrar toda a base

Inclui:

* `avisos.json`;
* arquivos dos módulos;
* índice dos módulos;
* materiais;
* eventuais dados complementares.

Minha recomendação para o MVP é:

> A interface editará `avisos.json` e permitirá consultar os módulos e aulas em modo somente leitura. A edição dos links dos módulos entra em uma segunda fase.

---

## 2. Definir como o projeto será localizado

O programa precisa saber onde está a raiz do site.

Algumas estratégias possíveis:

* caminho fixo configurado no código;
* seleção da pasta ao abrir;
* arquivo local de configuração;
* detecção automática procurando por:

```text
assets/data/avisos.json
assets/data/modulos/index.json
```

A solução mais prática é combinar seleção e persistência:

1. na primeira execução, o usuário seleciona a pasta raiz;
2. o caminho é salvo em uma configuração local;
3. nas próximas execuções, o programa tenta reabrir o projeto automaticamente;
4. caso os arquivos obrigatórios não existam, solicita uma nova pasta.

Exemplo de configuração local:

```json
{
  "projectRoot": "C:/projetos/arctel2026"
}
```

Esse arquivo não deve ser salvo dentro do site, mas na pasta de dados da aplicação.

## 3. Definir o modelo interno de dados

Embora o armazenamento seja JSON, a aplicação não deveria manipular dicionários soltos por toda parte.

É melhor criar modelos Python, por exemplo:

```python
@dataclass
class Notice:
    id: str
    titulo: str
    mensagem: str
    tipo: str
    data_publicacao: datetime
    ativo: bool

    data_inicio: datetime | None = None
    data_fim: datetime | None = None

    module_id: str | None = None
    lesson_id: str | None = None
    link_type: str | None = None

    static_link: str | None = None
    legacy_url: str | None = None

    texto_link: str | None = None
    prioridade: int | None = None
    arquivar_apos: datetime | None = None
    exibir_link_a_partir_de: datetime | None = None
```

Também convém ter modelos separados para:

```python
Module
Lesson
LessonLinks
```

Isso facilita:

* validação;
* preenchimento dos formulários;
* testes;
* serialização;
* mensagens de erro compreensíveis.

## 4. Definir as regras de validação

Essa é uma das decisões mais importantes.

O editor deverá impedir que um JSON inválido seja salvo.

### Campos obrigatórios

O formulário deve exigir:

```text
id
titulo
mensagem
tipo
dataPublicacao
ativo
```

### Tipos permitidos

O campo `tipo` deve ser uma lista fechada:

```text
confirmacao
ao_vivo
alteracao
alerta
material
encerrado
```

E `linkType` deve aceitar somente:

```text
teams
youtubeLive
youtubeRecorded
```

Esses valores estão definidos no contrato. 

### Fonte única de link

A aplicação precisa garantir que o aviso use, no máximo, uma destas alternativas:

```text
moduleId + lessonId + linkType
staticLink
url legado
nenhum link
```

Nunca duas simultaneamente.

Pode-se representar isso na interface por um seletor:

```text
Fonte do link:
○ Sem link
○ Aula de módulo
○ Link estático
○ URL legada
```

Na versão final, a opção `URL legada` provavelmente deverá existir somente para migração, não para criação de novos avisos.

### Datas de aula

É necessário decidir se a aplicação exigirá:

* ambos `dataInicio` e `dataFim`; ou
* nenhum dos dois.

Como a presença dos dois caracteriza o aviso como aula, o editor não deve permitir somente uma dessas datas. 

Validações adicionais:

```text
dataFim > dataInicio
arquivarApos >= dataInicio
exibirLinkAPartirDe <= dataFim
```

As duas últimas não são explicitamente obrigatórias pelo contrato, mas são regras de consistência recomendadas.

## 5. Definir como selecionar módulo e aula

O usuário não deveria digitar manualmente:

```text
modulo-2
aula-3
youtubeLive
```

A interface deve carregar:

```text
assets/data/modulos/index.json
```

e, ao selecionar um módulo, abrir o respectivo arquivo.

Fluxo sugerido:

```text
Módulo:
[ Módulo 2 — Desenho regulatório responsivo ]

Aula:
[ Aula 3 — 21/08/2026, 08:00–10:00 ]

Tipo de link:
[ Teams ]
```

Internamente, o programa grava:

```json
{
  "moduleId": "modulo-2",
  "lessonId": "aula-3",
  "linkType": "teams"
}
```

Os identificadores seguem o padrão sem zero à esquerda. 

---

## 6. Definir se o editor validará a existência do link

Ao selecionar uma aula e um `linkType`, a aplicação pode verificar se aquela URL já existe no arquivo do módulo.

Por exemplo:

```text
Módulo 2
Aula 3
Link: Teams

Status: link encontrado
```

ou:

```text
Status: a aula existe, mas o link do Teams ainda não foi informado.
O aviso será exibido sem botão.
```

Isso reproduz o comportamento atual do `notice-board.js`: o aviso continua aparecendo quando o link não existe, mas o botão é omitido. 

É importante decidir que isso será:

* um erro bloqueante; ou
* apenas um alerta.

Pelo contrato existente, deve ser apenas um alerta.

## 7. Definir o fluxo de edição

A interface principal pode ser dividida em três áreas.

### Lista de avisos

Exibir:

```text
Status
Título
Tipo
Publicação
Início da aula
Prioridade
Fonte do link
```

Com filtros:

```text
ativos
histórico
aulas
informativos
com link
sem link
legados
```

### Formulário de edição

Campos organizados em seções:

```text
Conteúdo
Agendamento
Classificação
Link
Arquivamento
```

### Pré-visualização

A imagem enviada mostra dois cartões principais e uma área inferior de atualização/histórico. A aplicação poderia apresentar uma prévia aproximada de:

* badge;
* título;
* mensagem;
* datas;
* texto do botão;
* ausência do botão quando o link não estiver disponível.

Não é necessário reproduzir todo o CSS do site na primeira versão, mas a prévia deve ajudar a detectar textos longos e inconsistências.

## 8. Definir o significado de “salvar”

Há pelo menos três ações diferentes:

```text
Aplicar alterações na memória
Salvar no JSON
Publicar no site
```

Essas ações não devem ser confundidas.

Uma solução segura:

* **Editar:** altera apenas o estado interno da aplicação;
* **Salvar arquivo:** grava em `avisos.json`;
* **Publicar:** opcionalmente executa Git, deploy ou outra rotina externa.

No MVP, eu deixaria a publicação fora da aplicação.

---

## 9. Definir a estratégia de gravação segura

Nunca é recomendável sobrescrever diretamente o arquivo original.

Fluxo de gravação:

1. validar todos os avisos;
2. serializar para um arquivo temporário;
3. testar se o JSON temporário pode ser relido;
4. criar um backup;
5. substituir o arquivo original de forma atômica.

Exemplo:

```text
avisos.json
backups/avisos-2026-07-26-103500.json
```

A aplicação também pode manter apenas os últimos 20 backups.

Uma decisão adicional é se os backups ficarão:

* dentro do projeto;
* fora do projeto, na pasta de dados do editor.

Minha recomendação é deixá-los fora do projeto, evitando que sejam publicados acidentalmente.

## 10. Definir a política de ordenação

O contrato informa que:

* `dataPublicacao` participa da ordenação e exibição;
* `prioridade` desempata ou favorece a exibição principal;
* `ativo: false` move o aviso ao histórico;
* `arquivarApos` também envia o aviso ao histórico. 

A aplicação precisa decidir se:

* preserva exatamente a ordem física do JSON;
* reorganiza automaticamente ao salvar;
* oferece um botão específico para ordenar.

É mais seguro preservar a ordem física e oferecer:

```text
Ordenar por publicação
Ordenar por prioridade
Mover para cima
Mover para baixo
```

Assim, o editor não altera silenciosamente o arquivo inteiro.

---

## 11. Definir como os IDs serão gerados

O campo `id` precisa ser estável e único.

Possibilidades:

```text
UUID
slug gerado pelo título
padrão semântico
```

Para esse projeto, IDs semânticos parecem mais legíveis:

```text
aula-modulo-2-parte-3
cronograma-confirmado-2026
material-modulo-4
```

A interface pode sugerir automaticamente o ID, mas permitir edição antes do primeiro salvamento.

Depois que o aviso já existir, convém avisar:

> Alterar o ID pode romper referências externas ou históricos.

Também deve haver validação de duplicidade.

---

## 12. Definir a política para URLs legadas

O contrato declara que o campo `url` ainda funciona, mas deverá ser removido após a migração. 

O editor pode oferecer uma tela de diagnóstico:

```text
3 avisos usam URL legada
2 podem ser vinculados a aulas
1 parece ser um link estático
```

Ações possíveis:

```text
Migrar para referência de aula
Migrar para staticLink
Manter temporariamente
```

Novos avisos não deveriam poder usar `url`.

---

## 13. Definir se haverá exclusão real

Para avisos, geralmente é melhor oferecer:

```text
Arquivar
Desativar
Excluir definitivamente
```

Como `ativo: false` já envia o aviso para o histórico, a ação padrão deve ser **desativar**, não excluir.

A exclusão definitiva deveria exigir confirmação e talvez só aparecer em um menu secundário.

---

## 14. Definir o tratamento de fuso horário

Todos os horários do contrato usam ISO com offset, por exemplo:

```text
2026-08-21T08:00:00-03:00
```

A interface deverá decidir:

* trabalhar sempre em `America/Sao_Paulo`;
* permitir escolher o fuso;
* preservar o offset originalmente informado.

Como o projeto usa `-03:00`, a primeira versão pode assumir Brasília, mas deve serializar explicitamente o offset.

Na interface:

```text
21/08/2026
08:00
Fuso: Brasília — UTC−03:00
```

No JSON:

```json
"dataInicio": "2026-08-21T08:00:00-03:00"
```

## 16. Definir o MVP

Um MVP razoável teria:

1. seleção da raiz do projeto;
2. leitura de `avisos.json`;
3. listagem de avisos ativos e históricos;
4. criação e edição;
5. seleção de módulo, aula e tipo de link;
6. validação dos contratos;
7. prévia básica;
8. backup automático;
9. gravação segura;
10. diagnóstico de URLs legadas.

Deixaria para uma segunda fase:

* edição de `modulo-N.json`;
* edição de materiais;
* integração com Git;
* publicação automática;
* importação/exportação;
* prévia idêntica ao site;
* histórico detalhado de alterações.

## Decisões que precisam ser fechadas agora

Antes de escrever o primeiro código, eu fecharia estas seis:

1. **O MVP editará somente `avisos.json` ou também os arquivos dos módulos?**
2. **A raiz do projeto será escolhida pelo usuário ou configurada previamente?**
3. **Link de aula ausente será apenas alerta ou impedirá o salvamento?**
4. **O programa poderá excluir avisos ou somente desativá-los?**
5. **A ordem física do JSON será preservada ou recalculada automaticamente?**
6. **A aplicação apenas salvará localmente ou também executará publicação/deploy?**

Minha proposta inicial seria:

> Editor local de `avisos.json`, com módulos em modo de consulta, seleção assistida de aula, validação não bloqueante para links ainda ausentes, desativação como ação padrão, preservação da ordem do arquivo, backup automático e nenhuma publicação automática no MVP.
